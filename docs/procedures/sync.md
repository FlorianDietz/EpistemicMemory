# Synchronization Procedure

LOG and SUMMARY files drift out of sync (an agent gets interrupted, or forgets to update the SUMMARY after LOG changes). This procedure fixes that.

1. **When to sync**: when the user asks (they write `!sync` or ask you to sync the logs), or when you suspect drift (SUMMARY dates older than LOG activity; a SUMMARY listing "unanswered" C: comments that have since been answered).
2. **How to sync**: launch one or more sub-agents, each tasked with:
   - Reading a LOG file and its corresponding SUMMARY
   - Checking that all key decisions, conclusions, and open questions in the LOG are reflected in the SUMMARY
   - Checking that all C: comments are accounted for (answered in the LOG → noted in the SUMMARY; unanswered → listed in the SUMMARY)
   - **Finding new C: comments via git.** List the C: lines added since the last sync: the added lines matching `^\+\s*C:` in `git diff <last-sync-commit>..HEAD -- convos/`, plus the same pattern in the uncommitted changes (`git diff`) and in untracked files under `convos/`. Taking both catches comments whether or not the user has committed them yet. `<last-sync-commit>` is the commit hash the previous sync recorded (step 5); if none was recorded, use `git log --since=<last-sync-date> -p -- convos/` instead. Private folders are gitignored, so git sees none of their comments: in `convos/{user}/private/`, grep for `C:` lines directly. Then read each candidate comment in context and check that it has an answer or a recorded decision (answered in a later entry, explicitly deferred or declined); text that merely sits near a comment may not answer it.
   - **Making cross-references two-way.** When this topic references another topic, ensure the other topic's SUMMARY carries a reverse "See also" backlink — and add the missing direction (annotated with *why* the topics relate), don't just verify it. An agent reading either topic should discover the other. When the other topic's pair is not itself part of this sync, adding the backlink there does not change that SUMMARY's `Last updated` date, since the date says when the content was last brought in line with the LOG.
   - **Checking for dropped promises.** Grep the LOG for agreed bookkeeping side-effects ("add X to FUTURE_WORK", "make sure we don't forget") and verify each was executed — these get silently dropped when a session's main deliverable ships. Also grep for **ownerless promises** ("whoever next touches", "someone should add", "a future agent should"): these usually never get done. Do it during the sync, or assign it to a named next task or person in the LOG.
   - **Consolidation check** (CLAUDE.md "Rewrite, don't patch"). Look for the patch pattern in each SUMMARY: more than one Status block, correction brackets or dated bullets next to the text they correct, several open-items lists, or an opening section that later content or a newer LOG entry contradicts. Rewrite the affected sections, opening state first, and delete what no longer holds. When you update a SUMMARY's status section, also re-read its other standing sections (open questions, next steps, open C:s) for statements the new state contradicts, and fix them in the same edit.
   - **Number corrections re-read the original data.** Before correcting (or "verifying") a specific number in a SUMMARY or LOG, re-read the file the number comes from (analysis output, results file); a LOG table or another SUMMARY is only a copy.
   - **Checking acronym expansions.** Agents tend to invent plausible expansions. When a change expands an abbreviation ("XYZ (Some Words)"), check the expansion against a file that defines it. If it is wrong, fix it (with an `OUTDATED:` note in LOGs); if no file defines it, ask the user rather than guessing.
   - Checking formatting compliance (epistemic markers, entry headers, dates)
   - Updating the SUMMARY if needed. Set its `Last updated` line to the sync date even when nothing needed changing (note "synced, no change"), so the next drift check doesn't flag the same pair again.

   Scripts and greps are welcome for finding candidates for any of these checks, but when they find nothing, that is not evidence: mechanical patterns miss anything written in a nonstandard way, so a clean script run never replaces reading.
3. **Private topics**: a PLOG syncs to its PSUMMARY, and — only if it contains shared-marked content — to a public SUMMARY per CLAUDE.md §Privacy. Sync agents operate only on the **current user's** files; syncing another user's private folder is never correct (on this machine it shouldn't even exist — flag it if it does).
4. **Scope**: a single pair, one user's folder, or the whole project.
5. **Afterwards**: in the README's Maintenance table, set the sync row's "Last run" date. After a whole-project sync (not after a partial one, which would make the next full sync skip comments in the files it left out), also put the commit hash it processed up to (`git rev-parse HEAD`) in the row's Notes cell. The next sync's search for new C: comments starts from that hash. If the project has removed the Maintenance table, add a one-line note with the date and hash to the README instead.
